大家好，这一集我们从最容易被忽略的地方开始：机器人会动，不等于它已经完成了导航闭环。我们参考 AIMA 技术开发指南的阶段结构，但本系列使用的是公开组件和自采的等价兼容资产，不是课程私有适配包，也不把这套流程包装成官方集成。

本集的验收目标很具体。第一，场景能够启动，G2 代理能够被定位，头部相机能够连续输出彩色图和深度图。第二，动作空间必须固定，模型只能看到 STOP、前进、左转和右转四个动作。第三，危险的前进动作要被安全门拒绝，而且拒绝以后位姿不能偷偷变化。最后，每次动作都要能和下一帧观测一一对应，之后才有资格谈数据采集和模型推理。

先看现场录屏。这里展示的是键盘验证程序，W 代表前进，S 只在 Stage 0 调试使用，A 和 D 分别代表左转和右转，Space 对应停止。进入训练动作空间以后，后退会被排除。四个模型动作的编码是固定的：STOP 等于 0，前进零点二五米等于 1，左转十五度等于 2，右转十五度等于 3。这个映射看似简单，却是后面数据标注、模型输出和适配器 API 之间最容易发生错位的地方。

为什么不能直接把键盘动作当成成功？因为键盘验证只说明控制端收到了输入。我们还要检查动作真的回到了仿真主线程，并且渲染帧、深度帧和位姿都对应同一个时间点。HTTP 线程只负责把请求放进队列，真正改变 Isaac 场景状态的动作由主线程执行。动作完成后至少等待两个渲染帧，再读取 RGB、depth、四乘四 pose、目标距离和碰撞状态。这样做是为了避免把上一帧的图像误配给当前动作。

接着看无遮挡前进。机器人向前移动零点二五米，前后位姿的平面位移模长应当接近这个数。这里我们不只看画面上机器人有没有向前，而是读取记录里的 pose 矩阵，计算 x、y 两个分量的差值。转向也采用同样的思路，十五度的增量必须在容差范围内。动作精度和画面观感是两件事，前者才是后续评测可以复核的证据。

再看近障碍拒绝。当前方头部深度的中心区域已经低于安全阈值时，安全门会把前进请求标记为 blocked。关键验收条件有两个：响应里要有 blocked 标记，机器人拒绝动作前后的位姿还要保持一致。如果只显示一张红色提示图，却没有记录前后 pose，那只能算界面演示，不能算碰撞安全验证。

在本实验中，适配器只监听本机回环地址的五八零二端口，不复用课程资料中未确认的 UDP 端口。这样做不是为了让系统显得更复杂，而是为了把已验证的接口边界说清楚。服务返回相对路径，所有路径解析以后还必须位于持久盘实验根目录内，避免日志把本机绝对路径、实例编号或其他连接信息带入公开素材。

画面里出现的流程图、箭头和颜色说明属于 AI 示意图。它们帮助观众理解感知、模型和动作之间的关系，但不作为指标来源。真实证据来自录屏、JSON 日志和截图；指标来源只有实验目录中的 eval_result.json。制作视频时，我们会在画面角落标注真实录屏、真实结果图或 AI 示意图，避免观众把示意动画误认为仿真原始画面。

这一阶段最常见的三个坑是：第一，动作编码在键盘端和模型端不一致；第二，动作返回以后立即抓图，导致 RGB、depth 和 pose 错帧；第三，blocked 只记录布尔值，却没有保留位姿前后对照。我们的验收卡把这三项都列成硬门槛。没有通过，就不进入 Stage 1。

最后总结。Stage 0 不是展示机器人走了几步，而是证明控制器具有可测的增量、可复核的观测和明确的安全拒绝行为。通过这一关，最多说明“仿真控制和观测接口可信”；它不能证明 StreamVLN 已经学会导航，更不能替代下一阶段的数据、训练和同批评测。下一集我们会把这些接口变成五十条训练轨迹和十条固定留出评测。

下面把接口层再拆开讲一遍，方便观众按自己的环境复核。reset 请求至少包含 schema_version、episode_id、seed、instruction 和 target_id。reset 返回第一张 RGB、第一张 depth、初始 pose、目标距离以及当前 episode 的状态。step 请求必须带唯一 request_id 和 action_id，重复 request_id 只能返回缓存结果，不能让机器人重复前进。close 请求负责结束 episode、写入轨迹和刷新 run-manifest。接口字段多并不是为了增加形式，而是为了让每一次动作都能找到对应的观测和文件。

如果服务收到非法动作，安全策略不是猜一个新的动作，而是把它转换成 STOP，并在日志里记录原始输出和转换原因。这样模型偶尔输出文本、空值或越界整数时，不会把未定义行为偷偷变成仿真动作。动作结果里的 terminated 和 truncated 也要分开：前者表示任务按规则结束，后者表示达到步数上限或被系统截断。两种结束原因对评测解释完全不同，不能只写一个 done。

观测同步可以用一个简单的时间线理解。HTTP 线程在时间点 t 提交请求，主线程从队列取出请求并尝试移动，渲染器在 t 加一生成新画面，至少再等一帧确认相机和深度更新，最后在 t 加二保存 RGB、depth 和 pose。若移动被 blocked，pose 应保持不变，但响应仍要有新的观测和 blocked 标记。任何一项缺失，都应该在采集器中直接报错，而不是在训练前静默补零。

路径安全也属于 Stage 0。接口返回的图像路径只允许是实验根目录下的相对路径。解析以后要做 realpath 检查，拒绝 `..` 穿越、绝对路径和符号链接跳出根目录的情况。公开日志中只保留相对文件名，不把本机目录、实例名称、网络地址或连接命令写进截图和视频。安全边界做得越早，后面整理公开材料越省事。

再看动作误差的验收方法。前进零点二五米不是要求浮点数永远精确到最后一位，而是要在配置定义的容差里稳定。转向十五度同样要读取四元数或旋转矩阵，计算平面 yaw 增量，而不是用肉眼判断画面转了多少。阻挡测试则相反，重点不是移动量，而是移动量必须接近零。将增量、blocked 和 pose 前后差写进一张小表，比只放一段视频更容易复核。

如果 Stage 0 失败，排查顺序应当固定。先确认场景和相机真的在主线程初始化，再确认请求队列没有重复消费，然后检查渲染帧计数是否增加，最后才检查深度阈值和 footprint。不要一上来调大安全阈值，因为这可能把碰撞问题变成假成功。每次修改都要生成新的 run_id，并保留旧日志，避免把失败版本覆盖掉。

这也是为什么本系列把“真实录屏”“真实结果图”和“AI 示意图”分开。录屏负责展示过程，结果图负责展示数值或前后对照，示意图负责解释关系。三类素材可以在同一章节出现，但不能互相替代。Stage 0 通过以后，我们才有一个可信的动作入口；真正的学习效果，仍然要等数据、LoRA 和 held-out 闭环共同回答。

实际复核时可以把本集暂停在四个位置：动作映射卡、两帧等待日志、危险前进前后 pose 对照，以及接口健康检查。每个位置都应该能回到一个文件或命令，而不是只依赖旁白。观众如果只想快速检查一件事，优先看 blocked 前后位姿是否一致；这项证据最能区分真正的安全门和单纯的界面动画。
