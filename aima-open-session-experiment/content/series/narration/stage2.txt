这一集我们讨论训练。标题里的问题是：loss 下降，为什么仍然不能说模型会导航？答案是训练指标和闭环指标测量的是不同对象。loss 只说明给定输入和标签时，优化器找到了一组更低的数值；它没有告诉我们模型在仿真里能不能理解目标、能不能选择安全动作，也没有告诉我们动作送回适配器后会发生什么。

先说环境隔离。Isaac Sim 使用预装的 Python 三点十一运行时，StreamVLN 的训练环境单独放在持久盘的 Python 三点九环境里。两个环境不能互相覆盖依赖。我们先锁定官方 Transformers 四点四五点一并验证 checkpoint 加载；只有在加载失败时，才按确定性规则升级到四点五一点零，并把最终依赖记录在 run-manifest。这样可以避免“为了能跑起来”临时改包，却无法解释结果来自哪套环境。

LoRA 配置是固定的：秩 r 等于八，alpha 等于十六，dropout 为零点零五，训练一轮，批量大小一，学习率二乘十的负五次方，BF16，开启 gradient checkpointing，并设置 mm_tunable_parts 等于 mm_lora_layer。这些值不是效果保证，而是复现实验的边界。视频里的配置卡只展示参数，真正的训练结果仍然来自日志和 JSON。

训练前先做 dataset-only 检查。它验证公开 annotations 能否读取、首动作是不是负一、图像路径是否存在、帧数与动作数组是否一致、sidecar 是否能够关联。然后做单 batch 前向和反向，检查输出、loss、梯度都不是 NaN 或 Inf。单 batch 通过后才开始完整训练，否则直接继续跑五十九步只会浪费时间和显存。

这次完整日志里有五十九个真实、有限且非零的更新步，loss 从零点四一六七下降到零点零八二三，峰值显存约二十七点一九 GiB。曲线说明优化过程发生过，但它没有证明模型理解“走向红色目标”这句话，更没有证明它能在新的相机观测里找到目标。我们把训练证据和导航证据分开放，就是为了不让一条漂亮的曲线替代真实闭环。

还要检查 adapter 重载。训练结束后，关闭当前进程，在一个新进程里只加载基础权重和 adapter，确认配置、参数形状、哈希和输出接口都一致。重载通过只能证明 adapter 文件没有损坏、依赖边界可复现；它不能证明新进程的动作已经接入 GenieSim，也不能证明 success、SPL 或碰撞统计会改善。

为什么不直接切四 bit LoRA？计划规定，BF16 只有在保留 OOM 证据后才允许切换。原因是量化会改变数值路径，如果没有先记录 BF16 的显存和失败现场，后面就无法区分“模型变好了”和“精度路径变了”。本轮显存没有触发 OOM，所以不把量化作为默认捷径。

训练日志还要做异常检查。除了 NaN 和 Inf，还要检查 loss 是否长期为零，梯度是否始终为空，更新步是否真的增加，adapter 文件是否有合理大小，以及保存时间是否和命令时间一致。上游模板曾经出现过静默回退到 qwen、日志显示零 loss 的情况，纠正后才得到五十九步真实更新。经验很简单：训练过程能跑完，不代表训练信号有效。

这一集的示意图会把数据、loss、梯度、adapter 和闭环拆成五个方块，并在角落标注“AI 示意图”。实拍画面则标注“真实录屏”，曲线和门禁卡标注“真实结果图”。这样观众能区分解释性动画与可审计证据。所有数字从唯一指标源或原始日志读取，不在剪辑软件里手工改数字。

训练阶段常见的误区有四个：把 loss 下降当成导航成功；只在原进程里加载 adapter；BF16 失败后没有保存 OOM 证据；以及把一条训练轨迹当成泛化评测。真正的验证要等下一集：同一批十条 held-out episode，基础模型和 LoRA 都重新 reset、重新清空 KV cache 和动作队列，由模型自己生成动作并驱动仿真。

所以 Stage 2 的结论不是“模型已经学会”，而是“训练信号、adapter 文件和加载路径可复核”。它为闭环推理提供了一个可重载的 LoRA 版本，却不预先承诺成功率。下一集我们会把 base 和 LoRA 放到同一批十条样本上，完整公开 success、SPL、距离、碰撞和动作统计。

把训练命令拆成四道门以后，日志会更容易阅读。第一道 dataset-only 只读文件，不申请显存，适合快速发现路径、schema 和图像数量问题。第二道单批前后向只运行一个 batch，记录 loss、梯度范数、参数 dtype 和显存峰值。第三道才是完整训练，写出每一步的 loss、学习率、耗时和 checkpoint。第四道关闭原进程，在干净进程里重新加载 adapter，并用同一个样本做一次确定性前向。

参数记录还应该包含模型 revision 和 tokenizer、视觉编码器 revision。计划中的 StreamVLN real-world checkpoint 与 SigLIP revision 只作为来源标识，不把基础权重或 adapter 放进 Git。训练结果可以保存 adapter 哈希、配置和日志摘要，但不能因为要做视频就把受限权重复制到公开素材目录。公开文章只讲接口、参数和验收逻辑，读者需要自行取得有权限的模型文件。

LoRA 的秩和缩放影响的是可训练参数路径，不是导航目标本身。r 等于八表示低秩更新的容量，alpha 等于十六控制缩放，dropout 用来减少过拟合，学习率决定每次更新的幅度。把这些参数写在封面上很直观，但不能把它们写成“保证成功”的配方。真正需要比较的是同一数据、同一评测协议下的闭环指标。

显存记录要区分峰值和当前值。峰值约二十七点一九 GiB 只能说明这次配置在 L40/48G 上完成了训练，不代表换成别的卡、别的 batch 或更高分辨率仍然安全。若出现 OOM，要保存完整命令、最后一个成功步骤、显存摘要和堆栈，再决定是否切换四 bit。没有证据就直接量化，会让后续复盘失去基准。

训练日志还要检查“看起来正常”的异常。loss 恰好全是零、每一步完全相同、梯度长期为空、更新步数比配置少、checkpoint 大小异常，都可能是模板静默回退或数据未被读取。一次上游模板回退曾经造成零 loss 假象，后来通过确认模型家族、打印 batch 内容和比较参数哈希才定位。视频里可以把这段作为排障示范，但不要把失败日志删除。

adapter 重载测试最好做两次。第一次只验证文件和配置，第二次让新进程读一帧公开 RGB，输出合法动作格式，再关闭进程。第二次仍然不是导航评测，因为它没有驱动仿真、没有累计路径，也没有达到目标的判定。它的价值是把“文件可加载”和“闭环可运行”之间的边界画出来，避免观众把加载成功误解成模型成功。

最后，训练报告应该把“能证明”和“不能证明”并排写。能证明的是数据入口可读取、数值路径没有 NaN、adapter 可保存和新进程可重载；不能证明的是相机域已经对齐、目标牌一定可见、模型会规划、success 会提升。把这两个列表放在同一页，比只展示一条下降曲线更诚实，也为 Stage 3 的失败结果留下解释空间。

如果观众要复核训练阶段，最小复现顺序就是先运行 dataset-only，再跑单批前后向，确认没有 NaN 或 Inf，最后才提交完整训练。任何一步失败都保留原始输出和退出码。这样即使最终导航仍然失败，也能知道失败发生在数据、数值、重载还是闭环，而不是把所有问题混成一个 loss 曲线。

把这一串门禁录进视频时，命令、日志和结果卡要保持同一时间顺序，观众才能看出每道门究竟验证了什么。
